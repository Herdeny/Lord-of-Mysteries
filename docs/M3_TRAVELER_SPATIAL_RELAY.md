# M3 旅行家持续双向远门

> 适用版本：0.9.29-1.20.1
> 状态：`code_ready`
> 设计基线：v0.9 旅行家序列 5“远门”纵切；仓库既有行为优先

## 1. 玩家目标

旅行家序列 5 可以把原版磁石指南针作为跨重启空间标记。手持有效标记按 `U` 后，
服务器在旅行家附近与目标磁石处生成一对持续 20 秒的真实双向门。玩家主动走入门体才会
传送；开门不会强制移动旅行家或附近玩家。

0.9.26 为标记增加服务端名称，为玩家增加持久黑名单，并把原版出生点保护与可取消 Forge
事件接入开门和穿门顺序。命名、访问模式和黑名单均由服务端裁决，客户端不能自报权限。

如果双手都没有指南针，`U` 保留原有“返回雾都前哨”兼容路线。只要任一只手拿着指南针，
能力就严格走磁石标记校验；未绑定、损坏或失效的指南针不会回退到出生点或前哨，也不会扣费。

## 2. 快速使用

1. 在原版磁石上使用指南针，生成带 `LodestonePos` 与 `LodestoneDimension` 的标记。
2. 输入 `/pm travel` 检查目标维度、坐标、名称、磁石状态、门持续时间、访问权限和黑名单数量。
3. 输入 `/pm travel name <名称>` 设置当前手持标记名称，或用 `/pm travel name clear` 清除。
4. 输入 `/pm travel access private|party|public` 设置之后开启的门。
5. 可选：用 `/pm travel block <在线玩家>`、`unblock <在线玩家>` 和 `blocked` 管理持久黑名单。
6. 旅行家手持有效标记按 `U`。
7. 等待两端门体出现；源门位于旅行家前方安全地面，目标门位于磁石上方。
8. 需要通行的玩家主动走入任一门体。抵达后获得 3 秒抗性 II，并有 2 秒反回弹冷却。
9. 用 `/pm travel doors` 查看自己当前已加载端点；需要提前收门时用 `/pm travel close`。

同一门主同时只保留最新一对门。再次成功开门会清除之前仍存在的端点，避免无限实体堆积。

管理员可用 `/pm travel admin doors <在线玩家>` 查询指定玩家的已加载端点，并用
`/pm travel admin close <在线玩家>` 撤销。普通玩家不能查看或操作他人的门。

## 3. 名称与黑名单

### 3.1 标记名称

- 名称写入指南针 `ProjectMysteryTravelMarkerName` NBT，随物品跨死亡、重登和重启保存。
- 名称按 Unicode 码点限制为 32 个字符；服务端移除 `§` 格式代码和控制字符，并合并多余空白。
- 空白名称等同于清除；未命名时显示目标维度和坐标。
- 两端门实体在生成时快照名称，设置实体自定义名，并写入 `door_name` NBT。
- 修改指南针名称不会追溯修改已生成的门；下次开门使用新名称。

### 3.2 持久黑名单

- 黑名单保存在门主 Capability 的 `traveler_door_blacklist`，最多 32 个去重 UUID。
- `/pm travel block` 与 `unblock` 当前要求目标玩家在线；`/pm travel blocked` 可查看已保存 UUID。
- 黑名单优先于 `party` 与 `public`：被拉黑者即使同队或面对公开门也不能通行。
- 门主始终保留通行权，避免损坏旧档或异常 UUID 让所有者被自己的门锁住。
- 开门时黑名单快照写入两端 `blocked_players` NBT；之后的 block/unblock 会立即更新门主当前仍存活的端点。
- 加载时会删除空值、非法 UUID 和重复项，并以确定顺序裁剪到 32 项。

## 4. 费用、寿命与冷却

| 项目 | 数值 |
|---|---:|
| 基础开门消耗 | 80 灵性 |
| 开门同行支持者 | +10 灵性/人 |
| 支持者上限 | 3 人 |
| 支持识别半径 | 4 格 |
| 双向门寿命 | 400 tick / 20 秒 |
| 标记名称上限 | 32 Unicode 字符 |
| 黑名单上限 | 32 个 UUID |
| 主持者再次开门冷却 | 36,000 tick / 1,800 秒 |
| 非门主再次作为开门支持者的冷却 | 1,200 tick / 60 秒 |
| 单次穿门反回弹冷却 | 40 tick / 2 秒 |
| 抵达保护 | 60 tick / 3 秒抗性 II |

开门支持者必须与主持者同维度、存活、非旁观、非睡眠、主动潜行、位于四格内、手持完全相同
的磁石标记且不在搭乘冷却。支持者只影响开门费用和邀请提示，不会被强制传送。

## 5. 两层明确同意

本实现把多人同意拆成两层，避免“站得近就被传走”：

1. **开门支持同意**：潜行、四格内、持相同标记，用于计算 `80 + 10 × 支持者`。
2. **最终通行同意**：玩家本人走入门体，才会触发黑名单、权限、领地和安全检查。

未潜行、拿错标记或不在四格内的玩家不会计入费用，但只要门权限允许且未被拉黑，他们仍可
在 20 秒内自行走入门。反之，即使某玩家在开门时被计为支持者，不进入门体也不会移动。

## 6. 访问权限

| 模式 | 命令 | 可通行者 |
|---|---|---|
| 私人 | `/pm travel access private` | 仅门主 |
| 队伍（默认） | `/pm travel access party` | 门主，以及开门时与门主同一原版记分板队伍且未被拉黑的玩家 |
| 公开 | `/pm travel access public` | 任意存活、非旁观且未被拉黑的玩家 |

门主在所有模式下始终可用。队伍名称与权限在开门时写入门实体快照；门存在期间改队或改权限
不会追溯修改已经生成的门。非法、空或旧档缺失的权限值由 schema 25 DataFix 修复为 `party`。

这里的“队伍”指原版 `/team` 记分板队伍，不读取客户端自报成员，也不允许一名玩家替另一名玩家
确认。被拉黑者或无权限者触碰门只收到限频拒绝提示，位置、灵性和冷却保持不变。

## 7. 领地兼容基础

0.9.26 建立不硬依赖第三方 Mod 的兼容顺序：

1. 开门前检查源端 `OPEN_SOURCE`；
2. 开门前检查目标端 `OPEN_DESTINATION`；
3. 每次穿门前检查目标端 `TRANSIT_DESTINATION`。

三项检查都会先执行原版出生点保护，再发布可取消的
`TravelerDoorTerritoryEvent`。事件提供操作者、门主 UUID、服务端世界、位置、门名和动作，
第三方领地 Mod 可在服务端取消。任何拒绝均发生在资源扣除或玩家移动前。

这是一层稳定的 Forge 兼容契约，不等同于已完成 FTB Chunks、FTB Teams 或其他领地 Mod 的
具体适配器。具体 Mod 的权限语义、组织权限映射和真人联调仍属于后续门禁。

## 8. 服务端安全顺序

开门全部由服务端执行，顺序固定为：

1. 验证旅行家序列、技能冷却和双手指南针 NBT。
2. 规范化标记名称、访问模式与黑名单快照。
3. 验证目标维度存在，目标坐标处于世界高度与 World Border 内。
4. 在加载区块后验证目标方块仍是物理磁石。
5. 为源端寻找坚实地面与两格无碰撞空间；验证目标端门体空间。
6. 预演源端与目标端的安全抵达位置，并拒绝过近标记。
7. 对源端和目标端执行出生点保护与可取消领地事件。
8. 收集最多三名开门支持者并计算精确费用。
9. 扣除灵性，依次生成源端和目标端实体。
10. 两端都成功后才清除旧门并开始 1,800 秒主持冷却；任一端失败会移除已生成端点并退款。

玩家穿门时会依次验证黑名单、访问权限、目标领地、目标维度、World Border、区块、坚实地面
与实体碰撞。目标失效时玩家留在原地，不写入穿门冷却，也不会被传到出生点。

## 9. 持久化与迁移

Capability schema 26 在 schema 25 远门权限基础上新增 `traveler_door_blacklist`。命名 DataFix
`traveler_door_safety_controls` 为旧档建立空黑名单；非法旧容器进入 `orphaned_entries`，
不会静默覆盖可审计载荷。复制、死亡重生、序列化、Provider 往返和 sanitizer 均覆盖该字段。

每个 `traveler_door` 实体保存：

- `owner`：门主 UUID，用于权限与单门主单对门约束；
- `owner_team`：开门时的原版记分板队伍名快照；
- `access_mode`：`private`、`party` 或 `public`；
- `door_name`：规范化后的门名；
- `blocked_players`：最多 32 个 UUID 的黑名单快照；
- `target_dimension`：另一端维度；
- `target_anchor`：另一端磁石或源门地面锚点；
- `remaining_ticks`：最多 400 tick 的剩余寿命。

门实体重启后只在仍有剩余寿命且字段合法时恢复。非法维度、缺失门主、非正寿命或损坏字段不会
构成可用门；损坏黑名单条目被逐项跳过，不会清空其他有效 UUID。乘客开门支持冷却写入服务端玩家
持久数据；40 tick 反回弹冷却只承担短时防循环职责。

## 10. 失败与恢复矩阵

| 场景 | 结果 |
|---|---|
| 未绑定指南针 | 拒绝；不扣灵性、不冷却 |
| 名称含格式码、控制字符或超过 32 字符 | 服务端清理并安全截断 |
| 黑名单损坏、重复或超过 32 项 | 删除坏项、去重并确定性裁剪 |
| 被拉黑者同队或穿公开门 | 原地拒绝；黑名单优先 |
| 原版出生点保护拒绝源端或目标端 | 开门拒绝；不扣费、不生成实体 |
| Forge 领地事件取消开门 | 开门拒绝；不扣费、不生成实体 |
| 门生成后领地权限改变 | 穿门目标事件拒绝；玩家留在原地 |
| 目标维度不可用 | 拒绝；不加载伪造维度 |
| 坐标越界或超出 World Border | 区块加载前拒绝 |
| 物理磁石被移除 | 标记失效；不回退出生点 |
| 源门无坚实地面或门体空间被占用 | 拒绝；不扣费 |
| 目标端无安全抵达位置 | 拒绝；不扣费 |
| 标记离源门过近 | 拒绝；避免重叠和循环 |
| 灵性不足 | 拒绝；不生成任一端 |
| 第一端生成失败 | 退款；不开始冷却 |
| 第二端生成失败 | 清除第一端并退款 |
| 外人触碰私人/队伍门 | 原地拒绝；限频提示 |
| 穿门后立即碰到目标端 | 40 tick 冷却阻止回弹 |
| 门存在期间目标变得不安全 | 玩家留在原地；门仍按寿命自然消失 |
| 重复成功开门 | 清除同门主旧端点，只保留最新一对 |

指南针与磁石始终不会被开门、命名或穿门消耗。

## 11. 自动化验证

当前发布门禁包含 416 项 JUnit 与 20 项 Forge GameTest：

- `M3TravelNetworkLogicTest`：费用钳制、支持者资格、20 秒寿命与反回弹常量；
- `TravelerDoorAccessModeTest`：门主优先、私人/队伍/公开、队伍规范化和非法值回退；
- `TravelerDoorPolicyTest`：名称消毒、Unicode 截断、黑名单优先、门主通行和确定性裁剪；
- `TravelMarkerServiceTest`：标记名称写入、清除与显示回退；
- `PlayerMysteryDataTest` / `PlayerMysteryDataFixerTest`：schema 25→26、复制、NBT 往返与坏值修复；
- 第 11 项 GameTest：真实磁石、源/目标门、精确扣费、未强制移动、20 秒寿命、开门冷却和失败保留；
- 第 15 项 GameTest：外人拒绝、原版队友通过、跨门安全落点、目标端防回弹及门 NBT 往返；
- 第 16 项 GameTest：命名双端一致、目的地领地取消不扣费、实时拉黑/解禁、门名与黑名单 NBT 往返，并验证门主/管理员查询与撤销双端；
- 第 17 项 GameTest：秘偶纵切，保证 M3 共用持久世界中的 schema 27 编队状态能与旅行家门状态并存；
- 第 18 项 GameTest：验证 schema 28 权威收纳记录、同 UUID 安全部署与复制凭证拒绝；
- 同一持久测试世界连续运行会使用本轮唯一特性来源，确保全服来源账本不会让复跑测试产生假失败。

CI 另外执行 M3 机器合同、资源/翻译/Pages 图鉴门禁、clean build、存档回滚和同一世界双启动专服矩阵。
